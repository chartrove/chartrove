# Supported JWT v5 migration and preserved token policy (#329)

The actual historical #329 patch adds an unused jwt/v5 requirement while
retaining jwt/v4 imports. This replacement changes both application module
graphs and all five affected production/test import sites to jwt/v5.3.1.
Only v4 removal/v5 addition appears in either selected module graph; all other
versions, toolchains, SQLCipher/provider replacements and prior checksum bytes
and order remain. Each sum file adds only the target module's two checksums.
The target has no runtime module dependencies and requires Go 1.21, below the
existing application minimum. [Head recovery](jwt-v5-head-recovery.json).

Upstream's [security policy](https://github.com/golang-jwt/jwt/blob/main/SECURITY.md)
supports v5 and reserves only possible critical backports for v4. The
[migration guide](https://github.com/golang-jwt/jwt/blob/main/MIGRATION_GUIDE.md)
changes the claims validation interface and skips issued-at checks by default.
A compile-compatible initial candidate reproduced acceptance of future-issued
tokens in both Go graphs. The same existing rejection tests pass unchanged after
adding explicit WithIssuedAt, WithExpirationRequired and HS256-only parser
options. The original algorithm guard remains. Not-before, empty-key, missing/null
expiry, expired, malformed, wrong-key, wrong-HMAC and unsigned-token rejection
remain covered. No issuer/audience restriction, clock leeway, token lifetime,
account role or signing-key migration is added.

## Validation and wire compatibility

The new boundary tests independently sign and verify the established HS256 wire
format using standard-library HMAC/JSON, retaining metadata, issuer, subject,
issued/expiry dates, jti and optional token fields. They pass on the original v4
implementation and on v5. Legacy user/access tokens generated by the unmodified
v4 application are accepted with every serialized claim intact by v5 in both
graphs. New v5 tokens are also verified by an isolated temporary v4 reader,
again with every claim intact. That reader is a test utility outside the
application graphs; neither production dependency closure imports jwt/v4.
Stored examples keep their real test-time expiry; they are not timeless fixtures.
Do not relabel newly generated v5 examples as original v4 evidence.

Both module verifications, root/desktop full vet, model tests, all desktop tests,
encrypted embedded-backend tests under the unchanged 120-second limit, upstream
JWT tests, auth race checks in both graphs and the server build pass.
Fresh govulncheck 1.9.0 symbol scans of auth (DB last modified October 27) show
zero called findings and zero JWT findings at any reported level in both graphs.
The required-module-only GO-2026-5932 advisory for deprecated x/crypto/openpgp
remains; those packages are absent from both production import lists. This is
not a whole-application clean-security claim. [Detailed validation](jwt-v5-validation.json).

Frontend inputs have no differences from qualified source 5ad6c590a. Fresh native
Go packaging will reuse that exact validated Zone frontend through the existing
--skip-frontend build mode, preserving/restoring original output trees. Native
package/signature/WebView acceptance and protected-main CI remain pending at
this source checkpoint. No real family or purchased Fasten data is used.
